# Yance.ai 当前状态基线

审计日期：2026-09-02

审计对象：仓库 `yance` 基线提交 `8cdf0e6`；Phase 0 在 `feature/investor-grade-upgrade` 收口

审计性质：静态代码、配置、迁移、测试、评测结果和运维文档审计；未修改业务代码、未连接生产数据库、未调用真实支付或模型供应商。

## 结论先行

Yance.ai 已经具备一个 Vertical AI SaaS 的可识别骨架：Next.js 营销站和工作台、FastAPI 多租户 API、PostgreSQL/pgvector、企业画像、政策库、匹配报告、任务与交付物、支付/发票对象、模型路由、评测目录和部署资料都已出现。

但当前版本仍应定义为 **可演示的 pre-production MVP**，不能定义为可安全收费、可承诺企业 SLA、可通过机构级技术尽调的生产产品。关键原因不是页面数量，而是收入、租户隔离、数据库迁移、AI 判定和安全声明等可信性基础尚未闭合。

在所有 P0 关闭前，建议：

- 暂停真实收费和自动开票；
- 将所有“已支付”“正式发票”“自动申报”“全量审计”“字段级加密”等能力声明降级为真实状态；
- 仅允许隔离的演示租户和非敏感演示数据；
- 不把现有 AI 资格判定作为无人复核的申报结论。

## 审计范围与方法

本次覆盖用户要求的 25 个检查面：repo、前端、后端、数据库、认证、租户、API、Agent/LLM、RAG、文档摄取、任务执行、支付、分析、Admin、日志、测试、部署、安全、技术债、死代码、重复代码、TODO、模拟能力、硬编码和生产风险。

已阅读 161 个 Git 跟踪文件的结构和关键实现；代码规模约为：Python 7,702 行、TSX 6,226 行、单一全局 CSS 5,357 行。Phase 0 使用 Python 3.12.13 隔离环境和锁定的前端依赖执行了真实基线验证：Next.js 生产构建通过；后端 5 个测试通过、总覆盖率 45%；Ruff 失败并报告 290 个问题；Eval runner 报告 2/2，但代码审计确认它只校验 case 结构；benchmark 因硬编码个人绝对路径失败。迁移链可解析为单一 head `20260817_0008`，但本机 PostgreSQL 和 Docker daemon 均未运行，因此没有把数据库迁移标为通过。所有结果详见 `15_PHASE_0_CHANGELOG.md`。

## 当前产品能力真值表

| 能力 | 当前状态 | 判断 |
|---|---|---|
| 企业注册与画像 | 部分可用 | 可创建租户、Owner 和基础 Company；画像主要依赖自由 JSON，缺少数据来源、验证、版本和完整度规则 |
| 政策知识库 | 部分可用 | 有 Policy 和 1024 维 embedding；全局政策与租户政策的 API 语义互相冲突 |
| 政策发现与匹配 | 部分可用 | 有向量 Top-50 + 规则加分；不是严格资格判断，缺少政策版本、引用片段和去重 |
| 资格判断 | 实验性 | 有 Evidence-Grounded 引擎和 benchmark，但当前准确率 43.8%、假阳性 28.6%，且存在安全事故条件被软化的逻辑缺陷 |
| 材料缺口 | 规则演示 | 由关键词生成通用清单，不是文档级证据差距分析 |
| 文档导入/RAG | 未完成 | 只有 OSS 预签名上传和对象存在检查；无解析、OCR、切分、向量化、ACL、检索与引用链 |
| 申报材料生成 | 未完成 | `application_draft` 仍运行同一政策报告管线；没有表单映射、模板渲染、字段溯源与人工审批 |
| Agent 任务执行 | 部分可用 | 有 Task/Deliverable/RevisionRequest/AgentRun；使用 Web 进程 BackgroundTasks，无持久队列、重试、锁和恢复 |
| 支付与权益 | 不可生产 | 有支付宝/Stripe 骨架和 Entitlement；演示支付可直接伪造支付，真实回调未可靠授予权益，银行路径运行时错误 |
| 发票 | 不可生产 | 创建逻辑写错对象；PDF 被标注“仅供内部对账”，不是税务发票；HTML 未转义 |
| Admin | 基本缺失 | 无平台管理员身份模型和管理前端；一个潜在全局任务接口存在路由遮蔽和跨租户风险 |
| Analytics | 基础事件表 | 有少量事件和统计，无漏斗定义、数据治理、归因、实验平台或外部产品分析 |
| Observability | 骨架 | 有 request-id、结构化请求日志和 AgentRun 表；无指标、trace、告警、错误聚合、SLO、成本账本 |
| 企业安全 | 不达标 | 应用层 tenant filter 为主，无 RLS；认证、审计、上传、密钥治理和安全声明均有重大缺口 |
| 部署 | 单机过渡态 | 后端 Compose 可描述本地部署；生产手册承认 Mac + Docker Desktop + Cloudflare Tunnel 单点 |

## 优点与可复用资产

- 技术栈简单、主流，FastAPI + SQLAlchemy + PostgreSQL/pgvector + Next.js 适合早期团队迭代。
- 租户 ID 已进入多数核心模型和对象存储 key，后续可以通过 repository/scoping 层和 RLS 加固，不必重写全部业务。
- Policy、PolicyRule、Opportunity、Application、Task、Deliverable、AgentRun 已形成合理的领域词汇雏形。
- 支付、产品 SKU、Entitlement 的对象方向正确，适合修成事件驱动的商业账本。
- 独立 policy engine、确定性 Gate、Golden Cases 和 benchmark 表明团队已经意识到 AI 可信度不是“Prompt 调优”问题。
- 报告带免责声明，且 benchmark 主报告公开未达标指标，这种透明度应继续保留。

## 审计边界与待验证事项

以下结论不能仅由仓库确认，必须在修复阶段补充运行证据：

- 当前线上 commit、数据库 migration head、生产环境变量与实际云资源；
- Cloudflare/WAF/HSTS、TLS、OSS 权限、云盘加密和真实备份；
- 支付宝/Stripe 商户配置、回调日志和结算对账；
- 模型供应商的数据处理条款、地域、保留策略；
- 域名邮箱、安全联系人、公司主体与隐私合规流程；
- 已有客户、真实活跃、收入、留存、报告准确率和人工服务成本。

## 开发准入 Gate

本审计完成后可以进入开发，但顺序必须是：先关闭 P0，再补 P1 的企业成交能力，最后扩产品。任何首页重做、动画或新渠道都不应绕过以下 Gate：

1. 从零迁移和关键 API 集成测试通过；
2. 演示支付在生产不可达，真实付款与权益原子闭环；
3. 跨租户安全矩阵通过；
4. AI 资格判断达到预设发布阈值并默认人审；
5. 对外安全/隐私/产品声明与可验证控制一致；
6. 有 staging、可回滚部署、备份恢复演练和基础告警。
